# 강화 확률·실제 적용 재검증

2026-11-10 · TLT-029/041/052/057/084 · QA/ENG · 0.97.2

사용자 요청으로 최신 Tempered6/4/30·Veteran15/10/50·Sentinel30/20/80에서 강화 수치와 확률 적용을 재검증한다. 프로젝트 제작 스킬 적용. 확률/비용/판정/저장 로직과 아이템 수치는 변경하지 않는다. 검사 중 강화 도움말이 최대MP·DEX도 강화된다는 사실을 누락하고 있는 것을 발견해 `AdventureText.EnhancementHelpIntro`와 개발 가이드를 정정했다. DEX 강화의 간접 공속/이속 효과 및 최대MP와 회복 비율의 구분도 설명했다.

`Enhancement.succeeds`는 서버 정수 roll0~9999를 `roll < 성공률×100`으로 판정한다. +9는0~1999 성공,2000~9999 실패이며 +1은 모든 유효 roll이 성공한다. 단계별 가능한10000값×9=**90000개 전체**의 성공 개수와 경계값을 검사했다. 실패는 기존 단계/옵션/장비를 유지하며 성공/실패 모두50Gold와 해당 단계 재료를 소비한다. Diamonds 비용은0이며 재료/Gold 부족은 강화 실패 영수증을 만들지 않는다. 특수 효과는 강화하지 않는다.

신규 `tests/enhancement-current-equipment.spec.lua`: 활성 가족40종+장신구3종에서 모든9목표·성공 마지막 값/실패 첫 값으로 실제 `InventoryRules.shop → EquipmentTransactions.apply`를 실행했다. +1은 실패값을 만들지 않는다. 수치·Gold/재료·소유/위치·원본 불변과 반대 roll로 재요청해도 결과/소모가 반복되지 않는 것을 포함해 **8044검사 PASS**.

기존 확률2869검사(90000값 열거 포함)와 현재 장비/인벤토리/스킬·삭제/시작장비 등 관련13묶음 총**14505검사 PASS**. [명령·결과](tests.log).

## 서비스 난수·엔진 재현 방식

`InventoryService.shop`은 접수한 요청의 서버 난수를 `shopPending.enhancementRoll`에 저장해 UpdateAsync 콜백과 SaveUnknown 재시도에 같은 값을 넘긴다. `MerchantService`의 Remote 허용키에 확률/난수 입력은 없다. 이미 확인된 요청을 다시 보내 서비스가 사용되지 않는 새 난수를 생성하더라도 저장된 영수증이 우선하므로 결과/차감은 바뀌지 않는다.

`python3 docs/evidence/enhancement-audit-20261110/make_native.py`는 현재 테스트와 실제 `InventoryService.shop` 본문을 바이트 수정 없이 추출해 격리 하네스를 생성한다. 추출 본문 SHA256 `d8e0c323d434c8a1db0dd8e988011519dab227feac5000e5503ab35ac857b9a9`. 서비스의 외부 의존성만 모의 계정/저장소/난수로 바꿔 실패 저장 후 응답유실·콜백2회·동일 요청 재시도/다른 요청 차단·명령변조 거부·새 요청의 성공을 재현한다. 실제 사용자 계정이나 라이브 DataStore에 시험 강화를 실행하지 않는다.

엔진 하네스는 실제 `Random.new(20261110):NextInteger(0,9999)`를 단계당100000회씩, 총900000회 표본 검사하고 사전 지정6σ범위와 비교한다. 고정seed는 QA 재현용이며 실제 서비스에는 지정하지 않는다. 이 유한 표본을 개별 사용자의 성공 보장이나 게시 서버의 관측 통계로 취급하지 않는다. API 범위/균등 분포 설명은 [Roblox 공식 Random 문서 원본](https://github.com/Roblox/creator-docs/blob/main/content/en-us/reference/engine/datatypes/Random.yaml)을2026-11-10에 확인했다.

같은 엔진 검사에서 실제 강화카드/도움말의9단계 성공·실패 표시와 서버 수치 일치, MP·DEX 도움말을 확인했다. 고정 소스 `d8daf8de3bef7df6459d603a88f4fb2712f21a24`를 origin/main에 푸시 후 단일 빌드 **0.97.2 성공**. `builds/0.97.2/TheLastThrone-0.97.2.rbxlx` SHA256 `35bcdffa848d8034cba662aa3214cbf16b297346ad8349e7d74769aa995c29ec`([기록](build.json)). `python3 tests/single-build.spec.py --artifact builds/0.97.2/TheLastThrone-0.97.2.rbxlx`: 역할10/도착로딩192·마운트/실제구성 PASS.

`run-in-roblox --place builds/0.97.2/TheLastThrone-0.97.2.rbxlx --script docs/evidence/enhancement-audit-20261110/native.luau`: 확률2869+현행장비8044+서비스본문18+강화화면19 = **10950검사 PASS**, 추가 **900000회 Roblox Random 표본 PASS**([로그](native.log)).

모든 표본은 사전 지정6σ 이내다. 표본별 실제 결과가 설정값과 정확히 같아야 한다는 뜻은 아니며, 유효 난수 전체의 성공 개수는 별도 전수 검사로 정확히 확인했다.

최초 엔진 하네스는 실제 서비스본문이 참조하는 `Rules`의 테스트 의존성 별칭을 누락해 실패했다([최초 로그](native-initial.log)). 외부 의존성에 `local Rules=R`을 연결한 뒤 같은 고정 게임 빌드로 재실행해 위 결과를 얻었다. 실제 서비스본문 해시는 동일하며 게임 로직은 바꾸지 않았다. 초기 스테이징의 생성파일 EOF 공백 검사도 수정했으며, 그때 커밋 전 HEAD를 대상으로 호출한 빌드는 기존0.97.1 파일 덮어쓰기 보호에 의해 차단됐다. 기존/신규 산출물을 덮어쓰지 않았고 이후 고정한0.97.2 빌드가 성공한 결과만 보고한다.

## 한계와 인계

실제 저장/게시 클라이언트의 사용자 계정 강화·실기기 입력·멀티서버/네트워크 수용은 미검증이며 QA 후속이다. 서버 함수 외부 의존성을 대체한 검사를 전체 InventoryService/실제 Remote 통신 실행으로 보고하지 않는다. 기존 단계별 확률·보정/천장 없음·현재 장비/강화 수치·가격/보유품을 유지한다. 로컬 고정 빌드 검증만 수행하고 Roblox 게시·사용자 Studio 적용·릴리스 태그는 하지 않는다. 별도 미커밋 자산과 TD 운영은 변경하지 않는다.
