# Ready 직후 Start 요청 유실 수정

2026-11-16 · TLT-053 / ENG · 사용자 보고: 3명 모두 Ready, 파티장이 Start를 눌러도 시작하지 않으며 오류 문구 없음.

## 재현과 수정

실제 요청 처리 코드를 실행한 회귀에서 다음 결함을 확인했다. Ready 또는 주기 GetState 뒤 0.35초 이내 Launch가 오면 서버는 실행 전에 ackOnly/Busy를 반환한다. 기존 클라이언트는 이 응답 뒤 Launch를 다시 보내지 않고 GetState만 조회한다. 조회 응답이 pending을 해제하므로 출발이 조용히 사라진다. 기존 파티 격리 검사는 명령마다 cooldown을 초기화해 이 경로를 검사하지 못했다. 이는 재현한 결함이며 사용자 실제 세 계정의 실패 원인을 확정한 것은 아니다.

- GetState 조회와 상태 변경 요청의 제한 시간을 분리한다. 자동 조회가 Start를 막지 않으며 조회 자체의 제한은 유지한다.
- 실행 전 ackOnly 거절에 한해 같은 명령·requestId를 대기 뒤 재전송한다. 중복 ack는 타이머 하나로 합치고 실제 응답/화면 제거 후 취소한다. 실행 여부가 불명확한 시간 초과는 기존대로 상태만 조회하여 Launch를 중복 실행하지 않는다.
- 서버 오류 안내를 주기 상태 갱신에서 지우지 않는다. 새 명령 또는 명시적 성공 응답에서 정리한다. Launch의 정상 거절 코드도 서버 warning으로 남긴다.
- 영웅 권한·준비/입장 조건·기존 규칙 보존·티켓·계정 저장·TD는 변경하지 않는다. 혼합 규칙 파티 차단은 유지하므로 그 경우 별도 안내/로그를 확인해야 한다.

변경 범위: ExpeditionService, ExpeditionView, 요청 회귀 검사와 기존 native 생성 도구, 빌드 VERSION. 관련 산출물은 이 폴더에 기록한다. 사용자 기존 자산 변경은 포함하지 않는다. 동시 별도 작업이 이미0.111.32 소스를 고정했으므로 이번 빌드는0.111.33을 사용한다.

## 검증과 후속

[기존 소스 실패](baseline.log): 같은 회귀에서 cooldown 뒤 원래 명령이 재전송되지 않아 실패한다. [수정 요청 회귀](request.log):30검사 PASS. Ready/Launch/Create/Join의 정확한 재전송, 중복/낡은 ack, 주기 갱신과 pending, 오류 유지/명시적 해제, 실제 응답 뒤 타이머 취소, 화면 제거, 불명 결과 재전송 금지, 서버 조회/명령 cooldown 분리를 검사한다.

기존 backend34·규칙183·출발42·Store43·안내94와 신규30, 총426검사 PASS. 실제 Studio Luau에서도65소스 컴파일 및426검사 PASS를 확인했다. 이는 순수 로직/클로저 검사이며 실제 프로필 저장·Player·게시 Teleport는 포함하지 않는다. run-in-roblox 포트가 별도 자산 검사에서 사용 중이어서 그 프로세스를 중단하지 않고, 열린 Studio의 Edit에서 DataModel을 변경하지 않는 순수 검사를 실행했다.
