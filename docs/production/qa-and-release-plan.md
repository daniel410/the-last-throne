# QA·수용·출시 계획

2026-10-28 · 담당: QA 에이전트 · 개발 문서 한국어 / 게임 영어(en-US)

현재는 제작 계획 단계다. 아래의 게임 테스트는 **실행 전**이며, 문서·이미지·계산 검사를 통과했다는 사실을 Studio 실행·실제 클라이언트·기기 성능·사용자 관찰의 통과로 확대하지 않는다. 최신 제품 계약은 [결정표](../decisions.md), 단계와 수용 범위는 [plan.md](../../plan.md), 실행 티켓은 [backlog.md](../../backlog.md)를 따른다.

## 1. QA의 책임과 증거 수준

QA는 제작자와 다른 관점으로 입력·상태·저장·오류를 재현하고 기대 결과를 대조한다. 엔지니어의 자체 검사와 QA 재검증을 함께 남긴다. QA가 출시 가능성을 보고하고 총괄 디렉터가 제공 범위·잔여 위험을 통합한다. 문서 작성만으로 게임 티켓을 완료하거나 실제 운영 반영을 수행하지 않는다.

| 증거 수준 | 확인할 수 있는 것 | 그 결과만으로 확인할 수 없는 것 |
| --- | --- | --- |
| 문서/컨셉 | 결정·상태·원천·공간/화면 의도 | 전투·저장·실제 영어 화면·조작성 |
| 정적 검사 | 링크 대상 존재·해시·ID·스키마·산술·의존 관계 | 재미·수령 처리·동시성·실제 프레임 시간 |
| Studio/엔진 | 상태/판정·모션·단일/다중 클라이언트·장애 주입 | 게시된 Place 이동·실상품 권리·실기기 성능 |
| 게시된 테스트 클라이언트 | 분리된 테스트 Experience 간 개인 이동·각 서버/접속 복구 | 미실행 기기/지역/부하나 운영 데이터의 호환 |
| 실기기 | 기록한 기기·OS·입력·옵션·세션의 실행/성능 | 모든 모바일/PC에서의 성능 |
| 사용자 관찰 | 기록한 참가자·과업의 이해·조작·실패 이유 | 시장 유지율·장기 수익·대규모 이용자 전체의 선호 |

각 결과에 `Planned / Pass / Fail / Blocked / Not Run / Not Applicable` 중 하나를 붙인다. `Blocked`에는 필요한 빌드/결정/기기를, `Not Applicable`에는 해당 공개 범위에서 제외한 근거를 적는다. 구현이 없으면 `Not Run`이다. 테스트ID는 회귀 때 유지하고 실행 결과에 빌드·데이터/자산·문자열·저장 계약 버전을 붙인다.

G2 대표 구간의 공개 테스트와 본편 전체 출시는 제공 범위가 다르다. D-12에서 실제 제공 범위와 표기를 정하기 전에는 범위 축소나 출시일을 확정하지 않는다. 각 게이트는 [backlog.md](../../backlog.md)의 해당 티켓 수용 조건도 충족해야 한다.

## 3. 테스트 카탈로그

다음은 테스트 설계이며 게임 실행 결과가 아니다. 버전별 데이터 행을 매개변수로 사용하되, 위험이 큰 권리/보상/전직 경계는 표본 몇 개로 전수를 대체하지 않는다. 구현 인터페이스와 D-결정이 고정되면 입력 fixture·장애 지점·검사 로그를 엔지니어와 연결한다.

## 4. 성장·32전직의 필수 매트릭스

[클래스/전직](../class-advancement-and-skill-trees.md), [스탯](../character-stats.md), [마법](../magic-schools-and-learning.md)이 기대 결과의 원천이다. Knight·Elf Archer·Dwarf Axe Thrower·Mage의 각2계열에 대해20/40/60/80 단계별 행을 만든다. 한 클래스가 통과해도 나머지24단계를 통과로 채우지 않는다.

각32행마다 `요구Lv-1 / 요구Lv / 요구Lv+1`, 미시험/시험성공·이미완료, 허용/타 클래스·반대 계열 요청, 정상저장/저장실패/재접속을 확인한다. Lv80 이후 지원 레벨이 없으면81 fixture를 정상 성장으로 만들지 않고 상한 초과 입력 거부 케이스로 둔다. 최초 계열 선택과 재선택 정책은 구분하고, D-04 미정인 재선택을 무료 확정 기능으로 만들지 않는다.

Mage는 비전/바람 훈련 어느 쪽에서도 Lv20 Pyro/Cryo 선택이 열리고 기초 물이 유지되어야 한다. Pyro 대지/Cryo 번개는 Lv40 자격·시험 후, 대규모 광역은 Lv60, 최강 주문은 Lv80 자격을 검사한다. 이름이 같은 공용 주문과 계열 고유 기술의 권리를 혼동하지 않는다. 강철기사 외 상위 명칭/영문 번역의 가칭 상태는 영어 용어집에 남긴다.

## 6. 동시성·장애·복구의 공통 절차

대상은 보상·포인트·instanceId 이동·수령 대기·리셋권·영수증·Diamonds다. 단일 DataStore 키 갱신 결과와 여러 키의 권리/아이템 거래를 구분한다. 구현의 실제 저장 순서를 [기술 계획](engineering-plan.md)에서 고정한 뒤 모든 중간 상태 fixture를 만든다. 문서에 ‘원자적’이라고 적은 것으로 동시성 검사를 대체하지 않는다.

1. 정상 실행의 시작 상태·처리ID·예상 권리/잔액/위치를 기록한다.
2. 같은ID 재전송, 다른ID의 같은 대상 경쟁, 두 서버/Place의 동시 요청을 각각 수행한다.
3. 검증 전, 예약/지속 기록 직후, 원본 변경 직후, 대상 변경 직후, 확정 직후/응답 전, 재개 중에 저장 실패·타임아웃·서버 종료를 주입한다. 적용되지 않는 단계는 이유를 적는다.
4. 이전 캐시·구버전 writer·순서가 늦은 응답을 추가해 과거 상태 덮어쓰기를 검사한다.
5. 같은ID로 조회/재처리하고 재접속한다. 실제 최종 상태와 지속 거래 기록이 일치하며 권리당 한 번·잔액 보존·아이템 단일 유효 위치로 수렴하는지 확인한다.
6. 실패가 계속되면 새 프로필/0잔액 저장이나 임의 재지급으로 처리하지 않는다. 소비/이동을 제한하고 사용자가 취할 행동을 담은 영어 상태를 제공한다. 수동 복구도 처리ID와 변경 전후 기록을 사용한다.

잔액/소유/지급 전후 기록·요청/거래ID·서버/Place·계약 버전·장애 지점·재시도 결과를 증거로 남긴다. 테스트 로그에는 결함 재현에 필요한 식별만 사용한다. 운영 계정/실잔액을 계획 검증용 fixture로 수정하지 않는다.

## 8. 게시된 테스트 클라이언트의 Place 이동·TD 회귀

Q-041의 필수 환경은 운영 데이터와 분리된 **게시된 TD 테스트 Experience와 RPG 테스트 Experience** 및 실제 Roblox 클라이언트다. Studio 다중 클라이언트 성공만으로 통과하지 않는다. 실제 Experience/Place ID·접근 설정·각 Experience 저장/상품 및 외부 지갑 테스트 구성을 조사해 기록한 뒤 실행하며, 현재 이 문서는 게시·상품 생성·운영 변경을 하지 않는다.

검사 순서는 기존 TD 신규/복귀 fixture의 시작 Place/영웅·Gold·Diamonds·구매권·성장 기록 → TD의 RPG Experience 개인 이동 안내/목적지 확인 → RPG 첫 방문/기존 캐릭터 재방문 → 성장/보상/구매권·외부 지갑 상태 확인 → RPG의 TD Experience 개인 귀환 → 기존 전투/저장/재접속 회귀다. RPG 생성/삭제나 왕복 자체로 Diamonds를 지급·복사하지 않는지 확인한다.

개인 이동 실패, 도착 직후 서버 종료, 출발 중 저장 실패, 구버전 서버, 직접 재접속을 추가한다. Experience 간 단체 이동/부분 도착은 초기 범위 밖이며 같은 Experience 안의 파티 이동에서 별도로 검증한다. 실패자는 재시도할 수 있어야 하며, 개인 선택 덮어쓰기·원정/보상 복제가 없어야 한다. TeleportData 변조로 돈/아이템/전직 자격을 발급하지 않는다.

결과에 실제 게시 빌드/서버 Job·Place ID, 이용자 fixture·파티/원정ID, 출발/도착 시각, 실패 코드/재시도, 전후 권리/잔액·진척의 검증 기록을 남긴다. 실상품 결제 결과는 별도 설정/권리 검사가 필요한 Q-034/039와 연결하며 테스트 영수증 시뮬레이션을 실제 Robux 결제 검증으로 보고하지 않는다.

## 9. 영어 전수와 결함 관리

영어 검사는 개발 문서의 한국어를 제거하는 작업이 아니다. 게임에 저작해 노출하는 문자열·이미지/간판·음성/자막을 대상으로 키/en-US 원문/분기/상태를 전수 추적한다. 퀘스트·NPC·전직/스킬·장비/상품·오류/복구·입력 안내·튜토리얼·설정/접근성·저널/엔딩을 포함한다. 사용자 채팅은 저작한 게임 콘텐츠와 구분한다.

정적 추출로 누락키·한국어 저작 문구·플레이스홀더·미정 용어를 찾고, 실제 화면의 빈 목록/잠금/가득 참/실패/대기/부분 성공·모든 선택 분기를 연다. 숫자·복수형·치환된 긴 이름·줄바꿈·포커스/터치 크기·게임패드 프롬프트를 검사한다. 컨셉 그림의 오탈자를 OCR로 가져와 영어 원문을 완성하지 않는다. 영어 효과 설명은 실제 데이터/상품 권리와 대조한다.

아래 심각도와 출시 처리 기준은 이번 제작을 위한 제안이다. 빈도/피해/회피 가능성·공개 범위에 따라 QA와 디렉터가 사유를 기록하고 분류한다.

| 심각도 | 예 | 처리 |
| --- | --- | --- |
| S0 치명 | 넓은 범위의 데이터 덮어쓰기·재현 가능한 결제/지갑/아이템 복제·복구 불가능한 권리 소실 | 관련 활성/출시 차단, 원인·영향/복구 확인 후 독립 재검증 |

## 10. 데이터 복구·릴리스 판정 패키지

출시 후보는 코드·콘텐츠/보상·영어·자산/공통 UI·스키마·상품 계약 버전을 고정한다. 변경이 생기면 영향받는 테스트만 재실행하고, 보상/저장/권리/공통 UI 변경에는 연결된 TD 회귀를 포함한다. 문서만 정리한 변경에 전체 실기기/결제 검사를 반복하지 않는다.

복구 리허설은 테스트 fixture의 보상/상품 지급 누락·중복 요청·창고 이동 중단·리셋 경쟁·부분 파티·스키마 불일치마다 탐지→기능 제한→처리ID/권리 조사→동일 계약의 재개/보정→이용자 결과 확인→회귀를 실행한다. 복구 작업 자체의 중복 요청도 검사한다. 지갑/아이템 거래 뒤의 최신 권리를 버리는 전체 프로필 롤백을 자동 처방으로 쓰지 않는다. 복구 가능 시점/자료·예상 시간·불가한 범위는 측정해 기록하며 임의 SLA를 약속하지 않는다.

| 제출물 | 판정에 필요한 내용 |
| --- | --- |
| 제공 범위/결정 | 공개 에픽/클래스·기기·선택 콘텐츠·제외 범위와 D-01~12 상태, 출시 안내가 실제 제공물과 일치 |
