[공통 지침](../AGENTS.md) · [에이전트](../agent.md) · [제작 스킬](../skills/the-last-throne-production/SKILL.md)

## 1. 작업 완료는 커밋과 푸시까지

사용자는 작업 완료마다 `git commit`과 `git push`, 빌드마다 메이저.마이너.마이크로 버전 생성, 릴리스마다 `git tag`와 태그 푸시를 요청했다. 큰 이미지와3D 모델링 파일은 Git LFS로 관리한다. 이 범위는 반복 확인 없이 실행한다.

한 작업의 구현/문서·관련 검증·필요 기록을 끝내고, 해당 파일을 선별 스테이징한 뒤 설명 가능한 커밋으로 묶는다. 기존 사용자 변경과 다른 에이전트의 미완료 작업은 보존한다. 초기 저장소의 첫 커밋은 검토한 기존 문서·컨셉·계산 도구·기본 프로젝트 뼈대와 운영 규칙을 기준 상태로 보존할 수 있다. 코드 뼈대 보존을 게임 기능 완료로 보고하지 않는다.

여러 에이전트가 같은 작업을 나눠 수행하면 각 역할은 검증 결과를 통합 담당자에게 넘긴다. 통합 담당자 한 명이 같은 브랜치의 스테이징·커밋·푸시를 순서대로 처리한다. 별도 브랜치/작업으로 분리된 경우에는 해당 작업 담당자가 처리한다.

마감 순서:

1. 변경 파일·작업 범위·현재 브랜치·원격을 확인한다.
2. 변경에 맞는 검증을 실행하고 실제 결과/미검증을 기록한다.
3. LFS 대상이 Git 인덱스에서 포인터로 저장되는지 확인한다.
4. 작업 파일을 스테이징하고 `git diff --cached --check` 및 스테이징 목록을 검토한다.
5. `git commit` 후 현재 브랜치의 추적 원격에 `git push`한다. 첫 푸시는 확인한 원격/브랜치에 `--set-upstream`을 사용한다.
6. 원격 브랜치의 커밋이 로컬 대상 커밋과 같고 LFS 전송도 성공했는지 확인한다.

무변경 상태에서는 빈 커밋을 만들지 않는다. 같은 원격에 이미 올라간 커밋은 재생성하지 않는다. 푸시가 거부되면 이력/원인을 확인하고 필요한 통합을 수행한다. 원격 이력 덮어쓰기·무조건적인 강제 푸시·LFS pre-push 훅 생략으로 성공처럼 처리하지 않는다.

## 2. 버전 형식과 증가

게임 빌드는 `MAJOR.MINOR.MICRO`의 세 정수를 사용한다. 예: `0.1.0`, `0.1.1`, `0.2.0`, `1.0.0`. MICRO는 흔히 PATCH라고 부르는 자릿수다. 문서 묶음의 `v0.25`, 콘텐츠/스키마 버전, 도구 버전은 별개다.

| 빌드 상황 | 증가 규칙 | 예 |
| --- | --- | --- |
| 기존 게임 빌드 버전이 없는 첫 빌드 | 개발 단계 기본 시작 버전 `0.1.0` | 없음 → `0.1.0` |
| 버그 수정·조정·재빌드 등 기본 경우 | MICRO +1 | `0.1.0` → `0.1.1` |
| 기존 계약을 유지하는 새 기능 묶음 | MINOR +1, MICRO=0 | `0.1.5` → `0.2.0` |
| 저장/공통 패키지/기능 계약의 호환이 깨지는 변경 | MAJOR +1, MINOR=0, MICRO=0 | `0.2.3` → `1.0.0` |

첫 빌드 때 루트 `VERSION`을 만들고 이후 이를 게임 버전 정본으로 갱신한다. 문서만 수정하거나 검증 계산기만 실행했다면 새 게임 빌드를 했다고 간주하지 않는다. 현재는 빌드 요청/실행이 없으므로 이 정책을 기록하기 위해 가짜 빌드 버전이나 릴리스 태그를 만들지 않는다.

빌드 입력을 고정하기 전에 버전을 예약하고 필요한 게임 표시/메타데이터를 연결한다. 소스와 `VERSION`을 커밋·푸시해 정확한 빌드 기준 커밋을 확보한다. 이후 해당 커밋에서 결과물을 만든다. 실패/중단한 빌드는 실패로 남기고 다음 시도는 다음 버전을 사용한다. 이미 사용한 버전으로 다른 바이트의 산출물을 덮어쓰지 않는다.

빌드 산출물/기록에는 게임 버전·입력 소스 커밋·도구/콘텐츠/자산/스키마 버전·실행 명령·결과 파일/해시·검증 상태를 연결한다. 빌드 후 증거 문서를 추가 커밋할 수 있으나 릴리스 대상은 결과물이 실제로 빌드된 소스 커밋으로 특정한다. `/build/`, `/builds/`, `/dist/`의 생성 산출물은 일반 소스 커밋에서 제외한다. 배포용 파일은 실제 릴리스 작업에서 정한 아티팩트 경로에 보존한다.

## 3. 릴리스 태그와 푸시

일반 커밋·일반 빌드·문서 완료를 릴리스로 자동 취급하지 않는다. 실제 릴리스 작업에서는 제공 범위·QA·데이터/상품·TD 호환·복구 등 해당 게이트를 확인한 다음 검증된 버전과 소스 커밋에 **주석 있는 태그 `vMAJOR.MINOR.MICRO`**를 만든다.

명령 예시의 버전/커밋은 실제 `VERSION`과 검증된 빌드 기록에서 가져온다.

```text
git tag -a v0.1.0 <검증된-빌드-소스-커밋> -m "The Last Throne v0.1.0"
git push origin v0.1.0
git ls-remote --tags origin refs/tags/v0.1.0 refs/tags/v0.1.0^{}
```

태그가 이미 있으면 먼저 버전·대상 커밋·배포 상태를 확인한다. 같은 릴리스의 재시도는 기존 태그를 검증하며, 다른 릴리스는 새 버전을 만든다. 태그를 강제로 옮기거나 관련 없는 모든 태그를 한꺼번에 푸시하지 않는다.

태그 푸시는 Git 릴리스 표식이다. Roblox Place 게시·상품 활성화·GitHub Release 생성/파일 업로드는 각각 해당 릴리스 작업의 실제 범위에 따라 실행하고 결과를 확인한다. Git 태그만으로 Roblox 게시까지 성공했다고 보고하지 않는다.

## 4. 이미지·3D·압축본은 Git LFS

[.gitattributes](../.gitattributes)가 LFS 대상의 정본이다. 확장자 규칙을 사용해 같은 종류의 원본을 일관되게 관리한다. 크기를 줄여도 기존 파일을 일반 Git과 LFS 사이에서 임의로 왕복시키지 않는다.

| 자산 | 저장 방식 |
| --- | --- |
| PNG/JPEG/WebP/GIF/AVIF 등 래스터 이미지, PSD/EXR/HDR/DDS/KTX 등 텍스처 원본 | LFS |
| Blender·FBX·GLB/GLTF·OBJ·STL·DAE·USD·Roblox 모델/Place 등3D 파일 | LFS. 생성된 빌드 출력의 ignore 규칙은 유지 |
| 자산 폴더의 외부 메시 BIN·ZIP/7z 컨셉/모델 묶음 | LFS |
| SVG·JSON·Markdown·스크립트·프롬프트·설정 | 일반 Git. SVG는 현재 텍스트 지도/도면이므로 diff 유지 |

LFS 설치는 이 저장소에 한정한다. 기존 훅이 있으면 내용을 확인하고 보존/통합한다. 훅을 강제로 덮거나 전역 Git 설정을 이 작업 때문에 바꾸지 않는다.

```bash
git lfs install --local
git lfs ls-files
git lfs fsck
```

새 작업 환경에서는 clone/checkout 후 `git lfs pull`로 실제 자산을 받는다. GitHub 원격의 일반 Git에는 작은 LFS 포인터가 저장되고 원본 바이트는 LFS 저장소로 전송된다. 포인터 텍스트를 실제 이미지/3D 파일로 착각하지 않는다.

기존 일반 Git 이력에 대용량 파일이 이미 있다면 `.gitattributes` 추가만으로 과거 이력이 바뀌지 않는다. 필요한 파일만 재스테이징하거나 이력 이전의 영향을 검토한다. 공유 이력을 재작성하는 `git lfs migrate`/강제 푸시는 일반 마감 과정에서 자동 수행하지 않는다. 이 저장소는 첫 커밋부터 LFS를 적용하므로 이번에는 이력 이전이 필요 없다.

## 5. 마감 보고

작업 결과에는 변경·검증·미검증과 함께 커밋ID·원격/브랜치·푸시 결과를 남긴다. 빌드를 했다면 버전/소스 커밋/산출물, 릴리스를 했다면 태그/대상 커밋/태그 푸시를 추가한다. 실패한 푸시는 성공으로 보고하지 않고 로컬 커밋·LFS 원본을 보존한다. 비밀·로컬 설정·OS 메타데이터는 커밋하지 않는다.
